# Phase 4: Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `apps/server`, the authoritative Fastify + PostgreSQL service: wallet sign-in (SIWE), `POST /actions` running game-core under a per-player row lock with idempotency keys and provably-fair seeds, Season Points accounting, server-side matchmaking and battle settlement, the token ledger (deposits via indexer, spend charges, withdrawal vouchers sized to the vault's daily cap), daily jobs, bans and rate limits. Plus `packages/shared`: zod schemas and API types shared with the web client.

**Architecture:** Thin Fastify routes call service modules; every service takes its dependencies (`db`, `clock`, `signer`, `chain`, `price`) as parameters so tests inject fakes. Persistence is Drizzle ORM over PostgreSQL; tests and local dev run on **PGlite** (Postgres-in-WASM, in-process, real `SELECT … FOR UPDATE` and transactions) and production on the `pg` driver with the same schema and queries. Player state is one `jsonb` row per player (the game-core `PlayerState`), mutated only through `applyAction`; every accepted action is appended to `action_log` with its seed so a season can be re-verified. Chain interaction goes through a `ChainClient` interface (viem behind it) with an in-memory fake for tests.

**Tech Stack:** Node 24, TypeScript 5 strict, Fastify 5, zod 3, drizzle-orm + drizzle-kit, `@electric-sql/pglite` (tests/dev), `pg` (prod), viem 2 (SIWE helpers, EIP-712 signing, `getLogs`), Vitest. No Redis: rate limits and locks live in Postgres.

**Spec:** `docs/superpowers/specs/2026-10-28-wyrmhaven-design.md` §12 (SP accounting; prizes are Phase 6), §13–14 (balance side of deposits/spend/withdrawals), §16–19. Contract ABI and rules: `contracts/README.md` ("Rules the server must follow"). Prior rulings: Phase 2 report (server builds `opponent`, battle seed revealed at battle start, state migration), Phase 3 report (voucher sizing, short deadlines, monitor `Claimed`).

## Global Constraints

- All money in integers: token amounts in wei (`bigint`), USD in micro-dollars (`bigint`). Postgres `numeric(78,0)` columns, mapped to `bigint` in TypeScript. No floats in balance math.
- game-core is the only place game rules live; the server never computes gold/food/XP itself. Server-side rules are limited to: auth, locking, idempotency, seeds, SP, ledger, chain, caps, bans.
- Every `/actions` call: `BEGIN` → `SELECT … FOR UPDATE` on the player row → derive seed → `applyAction` → settle effects → persist state + append `action_log` → `COMMIT`. One action at a time per player; a concurrent call waits on the lock. Repeated idempotency key returns the stored original response.
- Seeds (§17): per season a 32-byte secret `S`; `commitHash = keccak256(S)` published in `GET /season`. Action seed = first 4 bytes of `HMAC-SHA256(S, playerId ‖ ":" ‖ actionNonce)` as a `uint32` for `createRng`. Battle seed = `HMAC-SHA256(S, "battle:" ‖ battleId)`, **revealed to the client when the battle is created**. `S` is revealed at season end (Phase 6 job; the column and the reveal endpoint are built here).
- Errors (§19): game-core `ActionError` → HTTP 422 `{ error: '<CODE>' }`; auth 401; rate limit 429; idempotency replay returns the original status and body; server-side codes `INVALID_ACTION` 400, `INSUFFICIENT_TOKENS` 402, `BANNED` 403, `OFFER_EXPIRED`/`OFFER_NOT_FOUND` 409, `WITHDRAW_LIMIT` 422, `PRICE_UNAVAILABLE` 503.
- Daily caps (§16): PvP 20 and PvE replays 10 are enforced by game-core; SP 150/day and sell limit are server/game-core; the server adds per-IP and per-player rate limits (60 requests/min per player, 20 auth attempts/min per IP).
- Store prices are USD (micro-dollars, from game-core `priceMicroUsd`) converted to token wei with a `PriceSource` (30-minute TWAP in production; **`ManualPriceSource` set by an admin on testnet**, since no pool exists yet). Conversion: `tokenWei = ceil(microUsd × 1e18 / priceMicroUsdPerToken)`.
- Chain: Robinhood Chain testnet 46630 only; addresses from env; private keys only via env (`SIGNER_PRIVATE_KEY`, `OPERATOR_PRIVATE_KEY`) and never committed. Indexer treats an event as final after `CONFIRMATIONS` blocks (env, default 1 on testnet).
- Out of scope (Phase 6/7): season close and prize distribution, referral payouts, Telegram bot, admin UI, Uniswap TWAP implementation and ETH buyback execution (interfaces and stubs only), mainnet.

## Review Focus

1. Two concurrent `POST /actions` for the same player (same or different idempotency keys) → serialized by the row lock; the state after both equals applying them in sequence; a replayed key returns the stored body even if the state has moved on. (Task 4)
2. A client-supplied `opponent` in a `pvpBattle` body is ignored; the server substitutes the stored offer, and an expired, used or foreign offer id is rejected without touching the daily cap. (Task 6)
3. Withdrawal requests sized above the vault's remaining daily cap, or above the player's per-day allowance, are refused with `WITHDRAW_LIMIT`; an unclaimed voucher past its deadline is re-credited exactly once. (Task 7)
4. A banned player can still request a withdrawal of their own deposits (net of prior withdrawals) but nothing earned; all other routes return 403. (Task 8)
5. The indexer never credits the same `Deposited` log twice (restart mid-batch, reorg to the same tx hash) and never credits before `CONFIRMATIONS`. (Task 7)
